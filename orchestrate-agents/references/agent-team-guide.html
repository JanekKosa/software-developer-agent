How the agent team works

You talk to one chat. It hands each task to a lead, the lead hands each piece to a worker, and every result is checked by someone who did not build it. Everything that needs your say waits for you in the Decisions pane, out of the chat; you answer there or in the chat. Sizes and usage limits are handled without you.

At a glance
  • Four roles: the main chat, leads, workers, searchers. Only the main chat talks to you.
  • Work is cut into runs. Each run is one worker, one task file, one progress file, one report.
  • Every result is checked twice: by the lead, then by the main chat.
  • Every question, choice and problem goes into the decision register. You answer it in the Decisions pane or in the chat, and each answer reaches the main chat once. The chat names only a blocking one you have not answered yet.
  • An agent near its size cap, or the account near its usage limit, hands off and the work carries on.

Background

The words you need

The rest of the page leans on these, each with a small example.

Main chat (orchestrator)
The chat you talk to. It starts leads, passes your answers on, re-checks finished work, and commits only when you say so. It never builds and never starts workers itself.
Example: you ask for the invoice import; the main chat starts lead invoice-import.
Lead
An agent that owns one task. It plans the task, writes each worker's task file, starts the worker, answers it, and checks what it built.
Example: the lead splits the import into runs W1, W2 and W3.
Worker
An agent that builds and tests one piece, then reports to its lead only. It writes tests first and proves its work before it reports.
Example: worker W2 builds the duplicate check and its 12 tests.
Searcher
A cheap, fast agent that finds and quotes: file paths, line numbers, exact lines, counts. It never judges or recommends.
Example: "list every file that mentions InvoiceId" comes back as 14 paths with lines.
Run
One worker doing one piece, from its task file to its report.
Example: run W2, "the duplicate check", about 60 tool calls.
Task, progress and report files
The task file says what the run must do. The progress file is the worker's diary, kept from its first step. The report says what it built and what it checked.
Example: W2_TASK, W2_PROGRESS, W2_REPORT.
The four-line block
Every report ends with four lines: decisions taken, initiatives (things the agent did unasked), issues found, questions. The lead reads them to decide what must reach you.
Example: "INITIATIVES: added a test for an empty file".
Decision register
Two files of entries and one log: the open entries (each waiting for you or for an agent), the closed entries, and the answers log, which keeps every answer you ever gave. Each entry has an id, an urgency, a tiny example, the options, a recommendation, and what happens meanwhile. Only a script writes them.
Example: D-12 "Round VAT per line or per invoice?"; once closed, it ends with your final answer and a summary.
Context and its cap
Everything an agent has read and written so far, counted in tokens (word pieces). The cap is the size it must stay under: 400k for a worker, 500k for a lead and for the main chat.
Example: a worker is warned at 320k and closes with a report.
Hook
A small script Claude Code runs on its own at fixed moments. Two matter here: after every tool call (sizes and stops), and on every prompt you send (the register's reminder of blocking entries, which also hands the main chat any answer from the pane it has not had yet).
Example: after a read, a worker finds "you are at 322k of your 400k cap".
The three watches
Scripts running in the background, each shown in your task list by a name that says what it does. The Usage and context watch reads the main chat's log once a minute and your usage limits with a tiny Haiku call. The Decision answers watch hands your new answers to the main chat. The Agent size and stall watch follows one agent's size and whether it has gone quiet; a lead starts it only as a fallback. When the chat must act, a watch ends, and its ending notifies the chat.
Example: the chat sits idle at 452k; the Usage and context watch ends with SESSION NEAR CAP.
Hand-off and hand-over
A hand-off is one agent's note for its successor: done, checked, left, next step. The hand-over is the main chat's note for the next chat, naming every hand-off.
Example: a stopped worker adds "## Hand-off" at the end of its progress file.
Heavy command
A build, test run or type-check. On this 7.8 GB machine they take turns through one script, so two test runs never fill the memory at once.
Example: W2's test run waits 40 seconds for W1's to finish.

Step by step

What happens, and why

  1. 0

    You switch the team on for one chat

    • The agent types and the team's skills are linked into Claude Code, so every project has them. An ordinary chat uses none of them.
    • Type /software-developer-agent at the start of a chat. It marks that chat as a team chat, starts its Usage and context watch and its Decision answers watch, and loads the team's rules.
    • The hooks in your Claude Code settings (sizes and stops after every tool call, the register's reminder on every prompt) speak only in a marked chat and its agents. In any other chat they do nothing.

    Two chats open side by side: the one you started with /software-developer-agent shows both watches in its task list; the other shows none and behaves like plain Claude Code.

    After /clear, type /software-developer-agent again (your answer to D-35). Claude Code gives each chat an id, its session id, and the switch is kept per id. In the command's own words: "/clear switches the team off in a chat: it gives the chat a new session id, and the switch belongs to the old one. The Decisions tab closes and the hooks fall silent until the user types /software-developer-agent again (D-35). Reopening a chat from the history keeps its id, so the team stays on there." Example: your team chat shows Decisions (2); you type /clear, and within 2 seconds the tab is gone. You type /software-developer-agent, and the tab is back at the pane's next look.

    Why: your rule of 2026-10-26: "If i dont run the team agent, an oridnary chat is an ordinary chat with no processes etc".

  2. 1

    You ask for the work

    • In the switched-on chat, say what you want built: "build the invoice import".
    • The main chat fills in a short brief for the project: its rules, its checks, what is off limits.
    • It starts one lead per task. Several leads at once only when their files do not overlap and memory allows.

    Why: two agents on the same file overwrite each other's work; that rule has no exceptions.

  3. 2

    The lead plans and starts workers

    • It writes its plan in its own lead file: the runs in order, two lines each.
    • For each run it writes a task file and starts a worker on it. At most two workers at once.
    • While a worker runs, the lead ends its turn with WAITING FOR WORKER | W2 and costs nothing.

    Why: a run sized to about 75 tool calls fits under a worker's 400k cap with room to close properly.

  4. 3

    The worker builds and tests

    • It reads only what its task file names, writes the failing test first, then the code.
    • It keeps its progress file from its first step, so nothing is lost if it is cut off.
    • Builds and test runs go through the heavy-command script and take turns.
    • It never commits, never touches live systems, and never retries a command that timed out.
    • It ends with WORKER DONE | W2 | report: ... and the four-line block.

    Why: the four-line block is how its own choices and problems reach you, even the ones it thinks are small.

  5. 4

    The lead checks and registers

    • It re-runs the worker's checks itself and reads the changed files.
    • Anything you must see becomes a register entry: D-12, with an example and a recommendation.
    • A blocking question ends the lead's turn with QUESTION FOR THE USER | D-12. A non-blocking one is sent as a note, and work goes on with the recommended choice.
  6. 5

    You answer in the Decisions pane or in the chat

    • The pane appears only in a chat switched on with /software-developer-agent (step 0): it checks the same mark as the hooks. An ordinary chat shows no pane, even when entries wait in its repo.
    • The pane above the prompt shows every entry waiting for you: a tiny example, the options with what each costs, the recommendation, and what waits on it. An entry that came back to you shows its history above its choices: your earlier answers and each follow-up, oldest first.
    • The chat does not repeat it. Only while a blocking entry still waits for you does the chat name it in one line and ask you to answer it soon.
    • You pick an option and press Submit, or you answer in the chat; both count the same. Every answer goes into the answers log and stays there.

    "D-12: round VAT per line or per invoice? A 3-line invoice at 0.333 € VAT each gives 1.00 € per line and 0.99 € per invoice. Recommended: per invoice, as the tax office does."

    5a Your answer reaches the main chat once

    • An answer in the chat: the main chat records it at once and acts on it.
    • An answer in the pane: whichever comes first hands it over, the Decision answers watch or the hook at your next message. The watch hands answers over every 30 minutes, and at once when no entry is left waiting for you.

    Five entries wait at 10:00. You answer all five in the pane by 10:03. The main chat gets all five right after the fifth, not at the watch's next 30-minute turn.

    5b The entry is closed, or followed up

    • The main chat passes your words unchanged to the lead, and the lead on to the worker.
    • Settled: the entry is closed. It keeps your last answer as its final answer, and a summary of the decision.
    • Not settled: the main chat adds a follow-up (a note that explains, elaborates or talks about the decision further), and the entry comes back to you. A follow-up never changes the options; new options become a child entry, D-12-1 (your rule, D-15).

    Why the pane: your rule of 2026-10-26: the pane exists to keep the main chat clear, so decisions live there. You may still answer in the chat (D-18). Why a separate answers log: your answers do not fill up the entries, and the log keeps every one of them.

  7. 6

    The task ends

    • The lead ends with TASK DONE and a summary.
    • The main chat re-runs the full checks itself, and may run independent reviewers on the change.
    • It commits only with your go, only what was checked, and never pushes.
  8. 7

    Sizes and usage limits, without you

    • A worker near 400k writes its report and returns; the lead starts a fresh one for the rest.
    • A lead near 500k writes its lead file and the next task file; the main chat starts a successor.
    • The main chat near 500k, or your 5-hour or weekly limit near 95% or 98%: every agent writes a hand-off, the main chat writes the hand-over, and a new chat opens by itself one minute after the hand-over or the reset.

    The whole story: limits-and-caps-guide.html beside this page walks through each of these cases step by step.

Failure handling

When something fails

  • An agent is cut offBy the usage limit, an expired sign-in or a server error. Its work is fine. It is resumed while its cache is warm, otherwise a fresh agent carries on from its files.
  • An agent goes quietIts log file's last change is the sign of life. 40 minutes of nothing, with no long command running, means stuck; it is stopped and replaced from its files.
  • Claude Code restartsThe watches and every running agent stop; their files survive. The main chat starts its watches again and resumes warm agents.
  • The Decision answers watch failsAfter 3 failed looks in a row it ends with DECISION ANSWERS WATCH FAILED and the reason, and the main chat starts it again. When it fails twice in a row for the same reason, the main chat stops restarting it and tells you that line once. Your pane answers still reach the chat through the hook at your next message.
  • Memory runs lowHeavy commands wait for a free slot and 600 MB of free memory. A command that waits an hour gives up and says so.
  • A run's work is brokenThe lead re-runs the checks itself before the next run starts, and checks that nothing off limits changed, so a broken run is caught there, not at the end.
