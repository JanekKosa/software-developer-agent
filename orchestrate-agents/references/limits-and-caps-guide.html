What happens when a chat or an agent nears its limit

Two kinds of limit can stop work: an agent's own size cap, and your account's 5-hour and weekly usage limits. In every case the agents stop at a safe point, write down where they are, and the work carries on in a fresh agent or a new chat, mostly without you.

At a glance
  • A size cap belongs to one agent. A usage limit belongs to your account, so every agent reaches it at the same moment.
  • Agents are told while they work, at their next tool call, by the hook.
  • The Usage and context watch reads the limits and wakes the main chat when nobody is working.
  • Every stopped agent writes a hand-off. Hand-offs go up: worker, lead, main chat.
  • A new chat starts by itself one minute after the hand-over or the limit's reset.

Background

The words you need

The rest of the page leans on these, each with a small example.

Main chat (orchestrator)
The chat you talk to. It starts leads and passes your answers to them. It does no building itself.
Example: you ask for the invoice import; the main chat starts a lead for it.
Lead
An agent that runs one task. It plans the task, starts workers and checks what they build.
Example: lead invoice-import splits the task into runs W1 to W4.
Worker
An agent that builds and tests one piece, then reports to its lead.
Example: worker W3 writes the duplicate check and its tests.
Helper agent
A short-lived search agent. It finds and quotes, and never builds.
Example: a code-searcher lists every file that mentions a field name.
Context and its cap
Context is everything an agent has read and written so far, counted in tokens (word pieces). The cap is the size it must stay under.
Example: caps are 400k for a worker, 500k for a lead and 500k for the main chat.
Usage limit
How much your account may use in 5 hours and in a week. When it is used up, every chat and agent stops until it resets.
Example: the 5-hour limit is at 95% and resets at 17:00.
Cache
A saved copy of an agent's context. It makes the agent's next step cheap. It lasts one hour after the agent's last step.
Example: a lead last worked at 14:10, so its cache lasts until 15:10.
Tool call
One action an agent takes: reading a file, running a command, starting a worker.
Example: W3 runs the test suite. That is one tool call.
Hook
A small script Claude Code runs after every tool call of every agent, the main chat included. It can add a message to what the agent reads next.
Example: after a read, W3 finds "you are at 322k of your 400k cap".
Usage and context watch
A script that runs in the background beside the main chat; your task list shows it by this name. Once a minute it reads the chat's log file, and it asks Haiku (a small, cheap model) for the usage limits. When something needs doing, it ends, and its ending gives the main chat a turn. On this page, "the watch" means this one.
Example: the chat sits idle at 452k; the watch ends with SESSION NEAR CAP.
Decision answers watch
A second script beside the main chat, also named so in your task list. It hands your answers from the Decisions pane to the main chat. It plays no part in the limits, but every hand-over stops it too.
Example: at 14:25 the main chat hands over and stops both watches before it ends.
Helper service and pipe
A tiny program the watch or the hook starts only when a stop is needed. It answers the hook's question "should I stop?" over a named pipe (a private channel between two programs that lives only in memory). It tells each agent once, and lives until the main chat stops it after the hand-over, or the chat closes.
Example: the hook asks for W3; the answer is "STOP FOR LIMIT".
Hand-off and hand-over
A hand-off is one agent's note: what is done, how it was checked, what is left, the next step. The hand-over is the main chat's note for the next chat, listing every hand-off.
Example: W3 adds "## Hand-off" at the end of its progress file.
Relaunch
A Windows scheduled task opens a new Claude chat in this project's VS Code window, fills in "Read the hand-over and carry on" and presses Enter.
Example: the limit resets at 17:00; the new chat starts at 17:01.

The big picture

Who tells whom

The hook reaches agents while they work. The watch covers the times when nobody is working.

Where the state goes

Hand-offs go up, and come back down

Each agent writes its hand-off in its own file. The main chat's hand-over lists them all. The next chat hands each one back to the agent that continues the work.

The four cases

What happens in each case

Numbered as in your question. Cases 2 and 4 are one case: the usage limit is your account's, so the main chat, the lead and the worker reach it together.

  1. 1

    The main chat nears its 500k cap

    Purpose: hand the whole team over to a new chat before the main chat grows too big to think clearly.

    1. At 15:00 the main chat passes 450k. It hears SESSION NEAR CAP from the hook at its next tool call, or from the watch within a minute if it is idle.
    2. It finishes the edit it is in and starts nothing new.
    3. The helper service starts. W3 and the lead hear "this session is at its context cap and hands over" at their next tool call.
    4. W3 writes its hand-off and ends with WORKER STOPPED. The lead writes its own and ends with LEAD STOPPED.
    5. The main chat waits for every lead, with no time limit. At 15:12 it writes the hand-over, schedules the relaunch, and stops the helper service and both watches.
    6. At 15:13 a new chat opens by itself, reads the hand-over and starts the new lead.

    Why the stop goes to everyone: the old chat cannot talk to its agents once the new chat takes over. Left running, they would work on beside their successors.

  2. 2+4

    The 5-hour limit reaches 95% (weekly: 98%)

    Purpose: stop in the cheapest way. Resuming an agent whose cache is gone costs as much as rereading everything it read.

    The watch asks one question: will every agent's cache still be there 10 minutes after the reset?

    2a Every cache would survive

    The limit reaches 95% at 16:30 and resets at 17:00. Every agent's cache lasts past 17:10.

    • Nothing is done early. Everyone keeps working.
    • At 16:48 the limit is used up. The main chat, the lead and W3 are cut off.
    • At 17:01 the watch wakes the main chat. It tells the lead to carry on where it stopped, and the lead tells W3 the same.

    2b Some cache would run out

    The limit reaches 95% at 14:10 and resets at 17:00. The lead's cache would end at 15:10, long before the reset.

    • The watch starts the helper service, then ends. Its ending notifies the main chat, which starts a fresh watch to guard the hand-over.
    • W3 hears "STOP FOR LIMIT" at its next tool call. It writes its hand-off and ends with WORKER STOPPED.
    • The lead hears the same at its next tool call. It waits for W3, writes its hand-off and ends with LEAD STOPPED.
    • The main chat waits for every lead, with no time limit. At 14:25 it writes the hand-over, schedules the relaunch for 17:01, and stops the helper service and both watches: the Usage and context watch and the Decision answers watch.
    • At 17:01 a new chat opens by itself and carries on from the hand-offs.

    Why 95% and 98%: the stop itself costs a few steps per agent. The last 5% of the 5-hour limit and 2% of the weekly one leave room to write the hand-offs.

  3. 3

    A worker nears its 400k cap, or a lead its 500k

    Purpose: replace one agent with a fresh one. The rest of the team keeps working, and the main chat is not involved.

    3a A worker

    • At 14:20 W3 passes 320k. The hook says "stop building and start closing".
    • It finishes the edit, runs the tests, writes its report saying what is left, and returns.
    • The lead checks the report and starts a fresh worker W4 for the rest.
    • At 370k the hook says "STOP NOW": one progress-file edit, one report, done.

    3b A lead

    • At 430k the lead writes its lead file and the next task file. It returns LEAD HANDS OVER.
    • The main chat starts a new lead from those two files.
    • At 470k the hook says "STOP NOW".

    Why it stops so early: closing well takes about 25 tool calls, 60 to 80 thousand tokens. The warning leaves that room below the cap.

Failure handling

When something fails

  • The helper service failsIt did not start, it died, it stopped answering, or it gave an agent an error. The main chat is told first: LIMIT STOP SERVER FAILED, with what failed and when, from its hook if busy or from the watch if idle. Only then does it send "STOP FOR LIMIT" by message to each lead that has not stopped, and it tells you in its final message. A lead waiting on its worker reads the message only once the worker returns, so it arrives later.
  • A worker is inside one long commandIt hears the stop only when the command ends, for example a test run. Nobody cuts it short: the lead and the main chat wait.
  • The usage limit runs out before the leads stopEveryone is cut off. One minute after the reset the fresh watch notifies the main chat, which writes the hand-over from the files on disk and schedules the new chat.
  • Another VS Code window is in front at relaunchNo chat is opened in the wrong project. A Windows notification asks you to open a chat and names the prompt to send.
  • A server error, or a limit message with no readable reset timeThe watch notifies the main chat after ten minutes, so a short outage is over by then.
  • Your sign-in expiredWaiting does not help, so nothing wakes the chat. You sign in and continue.
  • You close the chatThe helper service quits with it.
  • You answer a decision after a hand-overThe old chat stopped its Decision answers watch. The answer waits in the register until the new chat's own Decision answers watch hands it over when it starts, or the new chat's hook does at your next message there.
