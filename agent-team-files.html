Every file the agent team uses

The team's files sit in three places. This repo holds what the team is; each project's repo holds what a task wrote; your home folder holds the links, and one state folder in it the logs and markers that make it run. This page draws each place and follows one task through them, file by file.

At a glance
  • This repo defines the team: three agent files, the main chat's skill with its hooks and scripts, the shared team rules, and 17 copied coding skills.
  • Claude Code finds it only through six junctions (folder pointers) in your home folder, and two hook lines in settings.json.
  • A task writes into its project's working folder: a brief, a lead file, a task, progress and report file per run, and a summary.
  • Every question goes into the project's decisions\ folder: the open file, the answers log, the resolved file. Only one script writes them.
  • new A chat uses the team only after you type /software-developer-agent, which leaves one marker file in the team's state folder. After /clear, type it again.

Background

The words you need

The rest of the page leans on these, each with a small example.

Repo
A project folder whose history git keeps. Its files can be committed and shared.
Example: C:\Repos\My projects\software-developer-agent is the team's repo.
Home folder and temp folder
Your home folder (~, here C:\Users\user) keeps settings that last. The temp folder (%TEMP%) is for files a program can afford to lose: a disk cleanup may delete old files there.
Example: ~\.claude\settings.json lasts; a file left in %TEMP% for a week may be wiped.
The team's state folder new
One folder in your home folder for every file the team writes for itself on this machine: ~\.claude\state\software-developer-agent\, with one child folder per kind of file. It is not in the temp folder, because a cleanup there would switch a chat off without a word (your answer to D-36).
Example: team-on\5f3c… says chat 5f3c… is switched on; logs\relaunch.log lists each relaunch step.
Junction
A folder that only points at another folder. Opening it shows the other folder's files, so an edit through it is an edit in the original.
Example: ~\.claude\skills\team-rules shows this repo's team-rules\.
Agent file
A text file that defines one kind of agent: its model, its tools, the skills it loads, and its rules.
Example: agents\task-lead.md makes the task-lead type, on Opus 5.5.
Skill
A folder with a SKILL.md of instructions. An agent loads it by name when it needs it.
Example: the lead and the worker both load team-rules at their start.
Hook
A small script Claude Code runs by itself at fixed moments. The team has two.
Example: after every tool call, context-guard.mjs checks the agent's size.
Watch
A script running in the background of the main chat. It ends when the chat must act, and its ending wakes the chat.
Example: the Decision answers watch ends when your answer arrives.
Transcript and session id
Claude Code's own record of a chat or an agent, one line per message. Each chat has an id (the session id), and many file names carry it.
Example: chat 5f3c… is 5f3c….jsonl; its agents are in 5f3c…\subagents\.
Working folder
The folder a task's files go in. The lead brief (the project's one-page rules for leads) names it.
Example: this repo's stage 2 used misc\implementation\agent-team\stage-2\.
Run files
A run is one worker doing one piece. It has a task file (what to do), a progress file (the worker's diary) and a report (what it built and checked).
Example: R1_TASK_CLAUDE.md, R1_PROGRESS_CLAUDE.md, R1_REPORT_CLAUDE.md.
Decision register
A repo's decisions\ folder: the open entries, every answer you gave, and the closed entries. Only the script register.mjs writes it.
Example: D-12 waits in the open file until you answer it.
Marker file
A small file whose presence, or one line in it, tells a script something.
Example: the context guard's marker remembers that W2 was already warned, so it is warned once.

Step by step

What appears where, and why

  1. 0

    Already in place, before any chat

    Business purpose: one copy of the team serves every project, and an edit reaches them all without copying.

    • This repo holds the team: three agent files, the orchestrate-agents skill, team-rules, and 17 copied coding skills.
    • scripts\install.ps1 made six junctions in your home folder. Claude Code finds the three agents, both skills and the /software-developer-agent command through them; Copilot finds both skills.
    • ~\.claude\settings.json runs the two hooks straight from this repo's path, each with a 10-second limit. It also keeps autoContinueAtUsageLimit off, and turns the Decisions pane on. The pane shows only in a chat you switch on (step 1).
    • The copied skills are not linked. The worker reads them by their full path.

    Why: a changed agent file reaches every project at the next Claude Code start (README). The skill folder is live: a saved edit reaches running chats at once (stage 2 lead brief).

  2. 1

    You switch the chat on new

    Business purpose: the team runs only in a chat that asked for it.

    • You type /software-developer-agent (your answer to D-33).
    • It runs scripts\team-on.mjs, which writes ~\.claude\state\software-developer-agent\team-on\<session id>. The file holds the time it was switched on.
    • From then on both hooks speak in this chat and in every agent it starts. An agent's hook input carries its main chat's id, so one marker covers them all.
    • In a chat without the marker, both hooks stop at once and say nothing.
    • The Decisions pane checks the same marker (your answer to D-34): when the chat starts, and at every look, every 2 seconds. With it, the pane shows. A chat switched on after it was opened shows the pane from the next look, without a reload. If the marker goes (deleted by hand), the pane closes at the next look.
    • In a chat without the marker the pane shows nothing: no tab, it never opens by itself, and it reads no register file. /decisions-pane there opens no pane and says: "The agent team is not on in this chat. Type /software-developer-agent to switch it on; the Decisions pane then shows here."
    • Right after the marker, the command starts the two watches (next step). Only a switched-on chat starts them.
    • Nothing removes the marker. A new chat has a new id, so it starts switched off.

    Chat A, switched on at 09:00, gets size warnings, decision reminders and the Decisions tab. Chat B, opened beside it at 09:05 for a quick question, gets none of them: no tab, even when entries wait in its repo.

    After /clear, type /software-developer-agent again (your answer to D-35). In the command's own words: "/clear switches the team off in a chat: it gives the chat a new session id, and the switch belongs to the old one. The Decisions tab closes and the hooks fall silent until the user types /software-developer-agent again (D-35). Reopening a chat from the history keeps its id, so the team stays on there." Example: chat A shows Decisions (2); you type /clear, and within 2 seconds the tab is gone. A comment typed in the pane but not sent is lost. You type /software-developer-agent, and the tab is back at the pane's next look.

    Why: your words of 2026-10-26: "i dont want the agent architecture to run for all main chats".

  3. 2

    The main chat starts its two watches

    Business purpose: something keeps an eye on usage limits, size and your answers while the chat sits idle.

    • The Usage and context watch writes ~\.claude\state\software-developer-agent\usage-watch\<session id>.txt: its process id and start time. A second copy for the same chat finds it and ends.
    • Every 60 seconds it reads the last 4 MB of the chat's transcript. It also reads the agents' transcripts and meta files, to see when each last wrote and whose cache runs out when.
    • It reads the shared usage reading, ~\.claude\state\software-developer-agent\usage-reading\usage-limits.json. When the reading is older than 15 minutes and the chat wrote since, it runs usage-probe.ps1. The probe makes one tiny Haiku call in the empty folder ~\.claude\state\software-developer-agent\usage-probe\ and rewrites the reading.
    • The Decision answers watch writes nothing itself. Every 5 seconds it checks the size and time of the open file and the answers log.

    Why: one reading serves every open chat, so three chats pay for one probe, not three.

  4. 3

    The brief, then the lead

    Business purpose: the lead learns this project's rules from one short file.

    • The main chat copies references\lead-brief-template.md to C:\Repos\Shop\temp\SHOP_LEAD_BRIEF.md and fills it in. The brief names the working folder, the status and sizes files, the checks, and the files no worker may touch.
    • It may also write a start file for the task. In this repo's stage 2 that was ANSWERS_LOG_TASK_CLAUDE.md.
    • It starts lead invoice-import. Claude Code writes the lead's transcript, <session id>\subagents\agent-<id>.jsonl, and a .meta.json beside it with the agent's type.

    Why: every lead reads the brief whole, so it holds only what changes from project to project.

  5. 4

    The lead plans in its lead file

    Business purpose: the plan outlives the lead that wrote it.

    • temp\IMPORT_LEAD.md: the runs in order, each decision with its reason, each run's state, the register ids, and what a successor must read.
    • temp\W1_TASK.md, written for a reader who starts cold: what to read, two points, the checks, and where W1's progress file and report go.
    • Before the run it lists the hashes (fingerprints) of the files W1 must not touch. In this repo those lists are <RUN>_HASHES_BEFORE.csv, kept out of git (D-30).
    • It reads SIZES.md at every wake-up, to cut the next run to fit.

    Why: the lead file is all that survives a cut-off. A successor lead carries on from it.

  6. 5

    A worker builds and reports

    Business purpose: one piece built and proven, with a diary a fresh worker could carry on from.

    • W1 starts temp\W1_PROGRESS.md at its first step and updates it after every point.
    • Its test run goes through run-heavy.ps1. While it runs, ~\.claude\state\software-developer-agent\heavy-commands\slot-1.txt says who holds the one slot.
    • After every tool call the context guard reads the last 512 KB of W1's transcript. Only when W1 passes its 320k warning does it write ~\.claude\state\software-developer-agent\context-guard\<W1 id>.json, so the warning comes once.
    • W1 writes temp\W1_REPORT.md, ending with the four-line block (decisions, initiatives, issues, questions).
    • The lead re-runs the checks, then adds one row to STATUS.md and one to SIZES.md.

    Why: nothing important lives only in an agent's memory. If W1 is cut off at its 60th tool call, a fresh worker starts from its progress file.

  7. 6

    A question goes into the register

    Business purpose: your decision waits where you can see it, out of the chat.

    • W2's report ends with a question: round VAT per line or per invoice?
    • The lead writes it to temp\entry.json: eleven fields, such as what, example, options and recommendation.
    • It runs register.mjs add. The script holds decisions\.lock for milliseconds and adds D-12 to OPEN_DECISIONS_CLAUDE.md, with status waiting-for-user.
    • Each write goes to a temp file beside the target, which then replaces it in one step. A reader never sees half a file.
    • Shop is not under C:\Repos\My projects\, so the register's files are also added to Shop\.git\info\exclude. Git then ignores them on this machine only.

    Why: one script writes the register, so the pane, the hook and the watch always read the same layout.

  8. 7

    You answer, and it reaches the main chat once

    Business purpose: your words reach the right agent, exactly once, unchanged.

    • The main chat is switched on, so the Decisions pane shows there. It reads the open file and the answers log every 2 seconds, and shows D-12.
    • You press Submit. The pane runs register.mjs answer. One line is added to ANSWERS_LOG_CLAUDE.jsonl: the id, the time, your words, and two times still empty. D-12 becomes waiting-for-agent.
    • Within 5 seconds the Decision answers watch sees the files change. No entry waits for you any more, so it hands the answer over: the line's handedOverAt gets the time, and the main chat wakes.
    • The main chat passes your words to the lead. The lead writes them into its lead file and passes them to W2.

    The log line, made up: {"id":"D-12","answeredAt":"2026-10-27 10:40","answer":"Chose B: per invoice.","handedOverAt":"2026-10-27 10:40","processedAt":null}

    Why: the log is never shortened. It keeps every answer you ever gave, so the entries do not fill up with them.

  9. 8

    The task ends

    Business purpose: a summary for the main chat, and a closed decision that keeps its final answer.

    • W2 writes temp\W2_REPORT.md. The lead checks it and writes temp\IMPORT_SUMMARY.md: what changed, what was checked, the register ids, each run's tokens and minutes.
    • The lead ends with TASK DONE | temp\IMPORT_SUMMARY.md.
    • The main chat closes D-12 with a summary. The entry moves to RESOLVED_DECISIONS_CLAUDE.md and ends with its Final answer, Summary and Resolved lines. The log line gets its processedAt time.
    • The working files stay. The watch's marker goes when the watch ends. The switch-on marker and the guard's markers stay in the team's state folder: no cleanup touches it, so they stay until you delete them.
  10. 9

    Only at a hand-over

    Business purpose: a chat near its size cap or a usage limit hands over to a fresh chat without losing work.

    • The watch writes its decision to ~\.claude\state\software-developer-agent\usage-watch\<session id>.decision.json: resume or hand over, the limit, the reset time, and when each agent's cache runs out.
    • It starts the limit-stop server. The server listens on a named pipe, \\.\pipe\claude-limit-stop-<session id>: memory only, no file. It logs to ~\.claude\state\software-developer-agent\logs\limit-stop.log.
    • Each worker adds a ## Hand-off section to its progress file; each lead adds one to its lead file.
    • The main chat writes the hand-over where the project's rules say. In this repo that is misc\handovers\.
    • schedule-relaunch.ps1 adds a Windows scheduled task, ClaudeRelaunch-Shop-<yyyyMMddHHmm>. It runs start-session-in-vscode.ps1, which logs each step to ~\.claude\state\software-developer-agent\logs\relaunch.log. The task deletes itself 12 hours after its start time.

    Why: the decision file keeps a restarted watch from taking a hand-over back.

    The whole story: orchestrate-agents\references\limits-and-caps-guide.html walks through each hand-over case.

Failure handling

When something fails

  • A marker is deletedA disk cleanup no longer reaches the markers: they sit in the team's state folder, not in the temp folder (D-36). If the switch-on marker is deleted by hand, both hooks fall quiet in that chat: no size warnings, no answers in prompts. The Decisions pane closes at its next look. Typing /software-developer-agent again writes it again, and the pane shows from its next look; team-on.mjs is safe to run twice. A lost guard marker only means a warning may come a second time.
  • You type /clear in a team chatThe chat gets a new session id, so the team is off there: the Decisions tab closes and the hooks fall silent. Type /software-developer-agent again (step 1). Reopening a chat from the history keeps its id, so the team stays on there.
  • Claude Code restartsThe watches stop; every file stays. A watch started again finds the old marker, sees that it names a dead process, and ignores it.
  • Two writers reach the register at onceThe second waits up to 10 seconds for decisions\.lock. A lock older than 60 seconds belongs to a crashed writer and is removed. The prompt hook waits only 2 seconds and leaves the answers for the watch.
  • The register is from an older versionIts ANSWERED_DECISIONS_CLAUDE.md is folded into the answers log at the next write. register.mjs migrate converts the rest.
  • The usage probe failsIt prints USAGE PROBE FAILED and writes nothing, so the last reading stays.
  • The limit-stop log cannot be writtenThe server does not start, because a failure would reach the main chat only through that log. The main chat is told, and stops its leads by message instead.
